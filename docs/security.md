# Security model (details)

> Status: 2026-11-24 · Platform implemented: macOS · Maintained with every change to sandbox, permissions or logins, every security review and every update of macOS, Claude Code CLI or Codex. · Summary: [SECURITY.md](../SECURITY.md)

This document describes in detail how `arr` tries to keep research agents from harming the machine they run on, which ways out we know of, and which of them are closed. It is written so that the general part can serve as a template for other operating systems and for servers. The platform part currently covers macOS only.

## 1. The conflict

`arr` runs groups of AI agents on hard mathematical problems. Many of these problems are open, some may not be solvable with the means at hand, and runs last for hours. To be useful, agents work without a human confirming every command: they write and run Python, create files and talk to each other.

A model that cannot reach its goal by legitimate means may look for other means: gaming a check, changing its environment or reaching for something outside its task. Released models are trained and tested against this, and in everyday use it is rare. It has been observed with models in development. In the OpenAI–Hugging Face incident of July 2026, agents ran on unreleased models with reduced safeguards, in training and evaluation runs where many tasks could not be solved legitimately. They left their sandbox through its one allowed network path and got into Hugging Face's infrastructure while looking for solutions. See [Wikipedia](https://en.wikipedia.org/wiki/OpenAI%E2%80%93HuggingFace_incident), [The Hacker News](https://thehackernews.com/2026/08/openai-says-reward-hacking-drove-ai.html) and [MIT Technology Review](https://www.technologyreview.com/2026/08/26/1143013/the-inside-story-on-why-openai-agents-hacked-hugging-face/).

`arr` uses released models and runs at a small scale. We still design for this case, for two reasons: hard research problems are the kind of long, demanding goal where it shows up, and without per-command confirmation the sandbox is the main barrier. Three goals follow:

1. **Agents have no reason to work around their limits.** "Not solved" is a valid result, and a blocked agent stops and asks.
2. **Limits are enforced, not requested.** The operating system and fixed rules enforce them, and tests prove them. We do not rely on goal 1.
3. **Runs are watched.** Approvals and decisions are logged, usage is counted per login, a kill switch stops runs, and real runs are supervised for now.

## 2. Threat model

**Attacker:** For design and tests we take the worst case. An agent in a run, or several working together, has shell access, file tools, time and the skills of a capable penetration tester. It tries to get around every limit, also over several steps and across turns, sessions and agents. This is a test assumption, not an expectation of how released models behave.

**Assets:**

- the user's logins: model subscriptions and API keys, the OS keychain, tokens held by other applications
- SSH keys, cloud credentials, browser data
- the user's files outside the run
- the network and other systems reachable from the machine
- `arr` itself: its settings, its start program, its permission rules
- budget and usage limits of the user's accounts

**Out of scope for now:** a malicious user, a compromised OS, attacks on the model providers' servers.

## 3. Principles

These hold on every platform.

1. **Test against the worst case.** A limit counts only if it is enforced by the operating system or by a fixed rule, and only if a test proves it with a counter-test (the test turns red when the protection is removed).
2. **Autonomy inside, approval at the edge.** Agents work freely inside the sandbox. Only the grey zone (network, package installation, reading outside the run) asks for approval. Forbidden actions are denied without asking. Because there is no per-command confirmation, the walls must hold on their own.
3. **Nothing outside the sandbox consumes what an agent can write.** No process outside the sandbox (agent CLI, app server, chat server, `arr` itself) executes code, loads modules or reads settings from a place an agent can write to, neither through the shell nor through file tools.
4. **File tools never get more than the shell.** Where tools such as Write or Edit run outside the OS sandbox, a fixed rule denies them every path the sandbox denies the shell, derived from the same source.
5. **An approval checks everything that follows it.** What an approval allows may run outside the sandbox. Codex, for example, applies an approved patch outside it. So the check covers every path, right and network target the action touches, not only the ones the request names first. Writing outside the run or onto protected paths is never approvable, not even by the user. A request the code cannot fully read is denied.
6. **Secrets never reach the agent.** No credential is placed in the agent's environment, files or logs. A small start program outside the agent's reach fetches it and hands it to the model client over a pipe.
7. **Fail closed, stop fast, count everything.** If a check cannot run, the run does not start. Every login profile has a kill switch that stops all runs using it. Usage is recorded per profile, request by request.
8. **Re-prove on change.** A version watcher forces the escape tests to run again after every update of the OS, the agent CLIs or their sandbox rules.
9. **Separate the user.** The last wall is an OS account of its own for the agents, without the user's logins and files. Until it exists, real runs are supervised.

## 4. Layers

| Layer | What it does | Decides |
|---|---|---|
| 0 Purpose | Prompts state the limits. "Not solved" and partial results are valid results; a blocked agent stops and says so or asks instead of retrying a denied step another way (the same text for both backends) | – |
| 1 OS sandbox | Every shell command: write only inside the run, read only from an allowlist, no network | kernel |
| 2 Fixed rules | Permission engine: hard denies (keychain tools, `sudo`, protected paths, `.git` via file tools, any file change outside the run, extra write roots, other agents' folders, this machine on the network) | code |
| 3 Approval request | Grey zone goes to an inbox with a one-line reason | – |
| 4 Decider | User, or a supervising agent within limits the user set | human / agent |
| 5 Outside hygiene | Processes outside the sandbox start isolated, with clean `PATH` and `HOME`, never from agent-writable places | code |
| 6 Watch and stop | Kill switch per profile, usage per profile, secret scan at the end of every run | user / code |
| 7 Separate OS user | Agents run as another account (planned; measured in a spike, see 5.3) | kernel |

## 5. macOS

### 5.1 How it is solved

- **Sandbox:** Claude's Bash runs under Seatbelt via the Claude Code CLI sandbox. Codex runs under its own sandbox with an `arr` profile that denies the home folder. Both write only inside the run and read only from an allowlist (work folder, shared run folders, read folders, Python environment).
- **Logins:** Credentials live in the macOS keychain or in the providers' own logins. A start program in `~/.arr/bin` (outside every write root, run with `python -I`) reads the secret and passes it to the CLI through a file descriptor (`CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`). It never appears in the agent's environment.
- **Keychain lock probe:** Before a run, a probe checks inside the sandbox that the keychain cannot be read.
- **Outside processes:** The CLI's `PATH` contains no write root; the run's virtual environment appears only in the agent's own shell environment. The chat server starts with `python -I`. The Codex app server gets a `HOME` of its own, outside the run's temp folder. CLI, app server and chat server find a `git` stub first on their `PATH` that does nothing, so no `git` runs outside the sandbox; agents keep the real `git` in their shell. The CLI runs with Node's compile cache off.
- **File tools:** One deny list in the permission engine covers `.git`, `.gitattributes`, `.gitmodules`, `.claude`, `.codex`, `.agents`, `.mcp.json`, shell start files and similar names, checked case-insensitively before and after resolving links. Write, Edit, MultiEdit, NotebookEdit and Codex file changes on these paths are denied, and no approval lifts that. The same list goes to the Claude sandbox as `denyWrite`. Codex `apply_patch` cannot be switched off, so the Codex profile makes the top-level names read-only and a patch there becomes an approval request that is denied.
- **Codex approvals:** Every Codex file change is checked with all its paths, the target of a move included. `arr` denies, without asking anyone: any move (the agent can use `mv` in its shell instead), any request for an extra write root (`grantRoot`), any write outside the run or onto the deny list, any change of an unknown kind or with unknown fields, and any command request with an unknown field, a value of the wrong type or extra permissions (`additionalPermissions`). A request method `arr` does not know gets a JSON-RPC error. A fixed test holds the methods, fields and value types against the schema of the pinned Codex version (with its experimental fields) and turns red on another version. `arr` runs no tool on behalf of the app server. An approved command still runs inside the sandbox, on both backends.
- **Waiting on a marker file:** An agent may wait for a file in its own work folder (`until_file`, for long scripts). This is the one place where something outside the sandbox looks at an agent-chosen path. The room server and the orchestrator only check whether the file exists: relative path inside the work folder, no `..`, no absolute path, no link followed, no content read, nothing started. Tests cover link chains, races between check and use, hard links and FIFOs.
- **Other agents' folders:** Inside a run, every agent's own folders are closed to all other agents: work copy, transcript, events, raw data, blobs, plugin, its `shared/` work folder, its temp folder and its scratch folder. Sealed reviews of other judges, sealed submissions (`groupchats/sealed/`), submissions on their way (`groupchats/staging/`) and the room database (`room.sqlite`, all channels) are closed as well. This holds for the shell on both backends and for Read, Grep and Glob, with no approval path, also under an "always" rule for the run folder or the work folder. A read rule written by hand for another agent's folder, temp folder or scratch folder does not open it either (way 9). Agents exchange work only through chat and results (`output/`). The one configured exception is a read folder `run:shared/<name>` set by the group's author; `check` rejects it where it would break the independence of judges or of isolated explorers. The run's Python environment stays shared on purpose; an agent can only use it as a drop on purpose.
- **An agent's own record:** Below its own `agents/<id>/`, an agent may use only its work folder and read its plugin. Its transcript, raw events, session, diffs and every other file `arr` keeps there, also one that appears later, are closed to it with no approval path, for the shell of both backends and for Read, Grep, Glob and every file change, also under a read rule written by hand.
- **Handover notes:** When an agent's context is full, `arr` asks it for a handover note and starts a new session with it. The note goes back only to the agent that wrote it; `arr` removes invisible and control characters from it and cuts it to a fixed length. While the agent writes the note, the group chat tools are refused for it (submitting, posting, asking, voting, waiting, reading), so this extra turn cannot act in the group.
- **Checking submissions:** In the phase model (`topology: phases`; phases `solo`, `parallel`, `chat` and `moderated` run, also with agents on `standby`, `folder: fresh` and `context: compact`) agents hand in their work with the room tool `submit`; the older tools `submit_result` and `submit_rating` were removed in wave 4b, and every run offers only `submit`. The check runs outside the sandbox and treats a submission as hostile data. Every field has a size limit (summary 800 characters, body 200 000, all field text together 100 000, 2 000 values, depth 4, integers up to 10^15); the walk is iterative and linear in the input; nothing in the data is run, evaluated or used as a path. Text is cleaned of control and invisible characters, and error messages quote names and values shortened and on one line. Files are copied by the rules for attachments: regular files below the agent's own work folder, no link anywhere on the path, no FIFO, no hard link, size limits. A submission is prepared in `groupchats/staging/` and moved into `output/` with one rename, inside the database transaction that numbers it. If the room server is killed between the rename and the commit, a folder without a database row stays behind; the next submission that needs the place moves it to `groupchats/staging/` under the write lock without following a link, and a `release` that was killed halfway treats what it already moved as moved. In a sealed stage a submission waits in `groupchats/sealed/` until the stage is released. The diff between two versions covers head, fields, body and files, never shows the content of a version that is still sealed, and runs in a process of its own (`python -I`, the texts passed as data) with a time limit. An agent's note to itself (`note_next`) is never written to `output/`. Tests kill the room server at these points, race links against the copy and let several processes submit at once. Accepted limit: in a sealed stage the number and the version of a submission tell an agent that someone else has already handed in, never the content or the real ID behind an alias.
- **Old topologies removed (W4b-06b):** Every run is a phases run; a run or group with an old topology is refused before it starts, at four places (planning a run, the skills catalog, the topology check and the run manager). Every check that ran on the old topologies now runs on phases runs: sealed submissions of an isolated phase cannot be read through the sandbox (shell, Read, Grep, also with an approval) and are released to `output/` on a stop and on an error; attachments refuse symlinks, hardlinks and a swap during the copy; tools never decide an approval, and resuming is blocked while an escalation is open; `decider: user` holds; the emergency stop per profile stops runs of the service and of `arr run`; the secret scan covers the scratch folders before they are deleted.
- **Phases and isolation:** A phase with `isolated: true` seals its submissions at the start of every pass and releases them after the last repetition of the last action, before a gate `judge` rates them; it also closes every channel the phase does not name, and only channels with the agent alone may be named there. While a phase is sealed, no other agent can read the submissions (`groupchats/sealed/` is closed with no approval path), the runner never gives one as an input, feedback or objection, and a wait for another agent's result does not end on a sealed one. After the release the runner reads every submission of the pass again; nothing it read while the phase was sealed is used afterwards. The only exception by design is `peers: summary`: per other agent, the newest summary it handed in in this pass before the current repetition began (with `over`, this can come from an earlier block of entries); never the agent's own. If the run stops or fails in the middle of an isolated phase, the runner releases the phase before it ends and no agent gets another turn; the submissions then lie in `output/`. If that release fails, the phase stays sealed; a regular end then fails with the error of the release, a stop stays a stop with the error in the log.
- **Agent text in the context package and the inbox:** Summaries, texts, file names, comments, objections and channel messages of agents reach another agent only as values inside a JSON block of the prompt (line breaks escaped, so no line can look like a heading of the prompt; the code fence is longer than any run of backticks in the block), cleaned of control, invisible and tag characters. When `content: full` reads a submitted file, `arr` opens it below the run folder without following a link at any part of the path and only reads a regular file. Each part of agent text and the whole package have size limits; when the package is too large, the feedback is cut inside first and the list of objections and the result of the gate go last. An agent with an alias (in an anonymous channel) is shown to every other agent only under that alias, also to agents outside that channel, in every part of the package; the real ID only appears in `arr`'s own records, which the other agents cannot read, and in texts to the user. `arr` does not search agent text for IDs: an agent that writes its own ID into its text gives it away itself. An agent's own note (`note_next`) only goes back to that agent with `context: compact`. The summary of an escalation lists one cleaned line per submission with Markdown marks escaped and a total limit. Assignment files are read once at the start from the run folder (the snapshot of the skill or project), by the rules of roles, with a size limit for the file and for the text after its placeholders are inserted (the values come from the user, not from agents).
- **Private channel to the user:** In a run with `topology: phases` every agent gets a channel `user.<agent-id>` before its first turn. Its only member is the agent; the user is the fixed address `user`. It is open in every phase, also in an isolated one. For every other agent it does not exist: reading, writing, `reply_to`, `thread` and `get_attachment` fail with the same message as for a missing channel or message, `list_channels` and the inbox do not show it, and no context package names it. Its files (attachments, the exported history) and `room.sqlite` are closed to other agents in both sandboxes exactly like those of any channel the agent is not a member of; this was tested with the real CLIs. As for any such channel, a read folder the group itself names, or an approval by the user, opens an attachment to Claude's Read tool (5.2, no. 22). The agent itself reads attachments of its private channel only through `get_attachment`, not through the shell. No agent can post as the user or as the orchestrator.
- **Own alias in an anonymous channel:** The project context tells each member of an anonymous channel its own alias there („In #judges you are ‚Mitglied B'“), from the same table the room uses. It names no other member's alias together with its ID, and a shared folder's context names no alias at all.
- **Channels per phase:** In a pass only the channels the phase names and the private channels are open; the room refuses every other one. While a pass runs, only its participants (agents with an action, on standby, raters) get hints or are woken; an agent that is a member of an open channel but not in the phase gets nothing and finds the messages unread later.
- **Waking agents on standby:** An agent on standby is woken only by a direct message to it (`to`/`@name`, a question to it, a reply to its message) in an open channel of the phase, by a note or a question of the user in its private channel (a question there counts as one to that agent, also without `@name`). A wake-up turn carries no expected submission, so the room refuses `submit` in it. Limits: `max_wakeups_per_agent` per pass, `turns_per_agent`, the ping-pong guard; when the actions of the pass are done no new wake-up turn starts, so agents on standby cannot keep a phase alive. An open question to the user holds a phase at most `user_question_hold_s` (5 min) after the question, after the actions of the pass (in `moderated` also when the lead's turns run out, and at the end of an assignment for its recipient's question) and only for an agent that has not handed in; handing in closes the question. Each answer gives one more turn within the channel's wake-up limit and `turns_per_agent`, so answered questions can extend the hold; a stop ends the wait at once. A note of the user that neither replies to the question nor names the agent (`@name`, `to`) answers no open question.
- **Assignments of a lead (`moderated`):** In a phase with `topology: moderated` the lead, the one agent with an action, can hand work to the agents on standby of that phase with the room tool `assign(agent, task, format)`. Every agent of a phases run is offered the tool, but the room refuses it for anyone who is not the lead of a running `moderated` phase: an agent on standby woken to answer, a recipient working on an assignment (no nesting), a rater, an agent of another phase, the lead after its submission was accepted or after the moderation of the pass ended, and every agent during the note turn of auto-compact. Refusals write nothing. The lead names a recipient as its context shows it, by its alias where the recipient has one, and no answer of the tool shows the ID behind an alias.
  - The text of an assignment is text of an agent, not an instruction of `arr`. It is cleaned (control, invisible, bidi and tag characters removed), limited to 4,000 characters (longer is refused, never cut) and shown to the recipient only in a section of its own, inside a fence that no run of backticks in it can close, below a fixed frame of `arr` that says who wrote it and that it changes no rights. It never appears in a header or sentence of `arr`, in `arr`'s run log, or in the prompt of the supervising agent. Recipient, format and limits come only from the arguments of the tool and from `run.yaml`, never from the text.
  - An assignment changes no right of its recipient: sandbox, profile, readable folders, tools and the decider of permission requests stay those of the agent in this phase (a phase or agent with `decider: user` stays tightened). At most `max_assignments` assignments per pass are allowed; counting and recording happen in one write transaction, so concurrent calls never pass the limit.
  - When the lead hands in while assignments still run or wait, `arr` names every one of them once and refuses the submission; the next `submit`, with no new assignment in between, is accepted and cancels them in the same transaction. If the lead's turns run out while it waits for an answer of the user, the phase is held as for any open question (at most five minutes); assignments it gives after the answer run as usual. Once the moderation of a pass has ended, no assignment is accepted any more. A cancelled assignment never starts, its running turn is ended the way `arr` ends a turn itself, and a later submission for it is refused. Submissions of assignments lie in the results folder like every submission; they are not submissions of the phase (no gate, no `from`, no `peers`), and their summaries reach the lead only as data.
- **Agent text in arr's own texts:** The texts `arr` writes for a wake-up, a hint or a continuation contain no text of another agent except the inbox in its usual form and, for `until_result_from`, the summary of a submission: cleaned, on one line, limited to 800 characters and marked as data. Every quotation mark of the Unicode categories Pi/Pf, every character named a quotation mark or corner bracket, and a list of look-alikes (low-9 marks, primes, ornaments, the ditto mark) are replaced in it, so a summary cannot close `arr`'s quotation marks with any of these. Hints and wake-up reasons name no sender; the wake-up of `until_result_from` names the awaited agent as the waiting one sees it (its alias in an anonymous channel); the name of a private channel appears only in texts to its own agent. Sealed submissions end no wait and are not shown.
- **Temp folder per agent:** Each agent gets `tmp/<id>/` as `TMPDIR`, as `CLAUDE_CODE_TMPDIR` (through a short alias `/tmp/arr-<hash>` of its own) and, for Codex, as its command `HOME`. Output of background commands lands there too.
- **Scratch folder per agent:** Each agent gets `scratch/<id>/` (`ARR_SCRATCH`) for throwaway data: writable for it, closed to the others like the temp folder. It is emptied, without a diff, with a fresh work folder and at the end of the run. At the end of `arr run` the secret scan still sees it: `arr` first moves it into a folder closed to all agents and deletes it only after the scan. If the scan itself fails, the parked folder is deleted all the same, unscanned. If `arr` ends before that step, it stays there until the run is slimmed. Scratch content removed together with a fresh work folder during the run is not scanned.
- **Fresh work folders:** In the phase model a phase can give an agent a fresh work folder (`folder: fresh`). `arr` runs outside the sandbox, so in a folder an agent can write to it never writes, moves, deletes or changes rights through a path whose parts the agent could swap: it opens the folder once, without following a link, checks that it is the folder it found, and works relative to that handle from then on. It moves the old content entry by entry, without following a link and without reading it, to `retired/`, which is closed to every agent, the former owner included, with no approval path, also under a read rule written by hand. It builds the fresh content from the run's own snapshot (never from the project as it is now) in a folder no agent can reach and moves it into the same directory without replacing any entry there. Then it compares the folder with what it put there. Extended attributes, the ACL and the file flags of the work and scratch folder themselves are removed, and both folders get the mode and times a new one would have. If something the agent's processes did would stay (an entry `arr` cannot move, a name planted in the folder, anything else in it), the run stops with the path instead of going on in a half fresh folder. If `arr` is killed in the middle, a half-built folder stays in `retired/`, closed to every agent, until the run is slimmed; the clean-up at the end of a run also removes such leftovers.
- **What a fresh work folder does not take away:** A process the agent started and that is still running keeps what it holds: a file of the old folder it holds open stays readable and writable for it, a mapped file stays readable, and a folder it holds open still lists its names. By a path, also relative to its old working directory or through a held folder, it reaches nothing of the old folder. What it writes into the fresh folder after `arr` finished is not removed. The temp folder `tmp/<id>/` and the run's Python environment live on for the whole run; a hard link from there to an old file keeps that file. Layer 7 closes the processes.
- **Deleting agents' files:** Cleaning up at the end of a run, emptying a scratch folder and slimming delete only through folder handles and never follow a link. Rights, file flags and ACLs are changed only on the entries reached that way, so a folder an agent's process swaps for a link while `arr` deletes never leads `arr` outside the run.
- **This machine on the network:** Requests to `localhost`, `127.0.0.0/8`, `::1`, `0.0.0.0`, `*.localhost` and the service's random host name are denied by a fixed rule, without asking and also under an "always" rule. Wildcard hosts that include this machine (`*`, `*.*`, `*.localhost`, `127.*` …) never reach the sandbox's `allowedDomains`, and a rule containing one does not load. Measured: the Claude sandbox's proxy does not block loopback by itself, so this protection rests on `arr`'s rule alone. Names that resolve to `127.0.0.1` through DNS can still be approved; the `arr` service answers only under its random host name.
- **Claude Code bridge:** `arr mcp` is a stdio server that Claude Code starts in a project. It reads the address, host name and token of the running service from `service.json` (mode 0600) at run time only and never puts the token in its command line or environment. The service answers only under its random host name (check against DNS rebinding) and only with the token.
- **Run starts from Claude Code:** Every run that Claude Code starts waits for the user's approval in the GUI. The card lists every deviation that widens rights: web, read folders, work folder mode, decider, limits above the standard, other profiles, extra agents, terminal. No tool can approve a run start, decide an approval or escalation, or answer an agent's question to the user. A message from Claude Code wakes an agent but never answers its question, also when it addresses or replies to it. Claude Code cannot set the supervising agent's mandate or model.
- **Agent text to Claude Code:** Agent text that reaches Claude Code is marked as data and cleaned of control, invisible format and tag characters. Error messages never quote argument values.
  - Claude Code reads submissions through `read_results` with the same limits as other agent text (`agent_text`, page budget). There, sealed submissions of an isolated phase are only counted until the phase releases them. Claude Code may read an agent's private channel but cannot write into it: `post_to_run` refuses, so an agent never takes a message of Claude Code for the user's answer.
  - **Known limit:** the transcript of an agent is the complete record. It shows the arguments and the output of every `submit` call, including `note_next` and the content of a submission that is still sealed, both in the GUI and to Claude Code through `read_transcript`. The sealing therefore holds against the other agents of the run (they cannot read the transcript, see "Other agents' folders"), not against a reader of the transcript. Claude Code is told not to pass anything from a transcript or a submission on to other participants during an isolated phase. Whether Claude Code should not read transcripts while a phase is sealed is open (planned for wave 5).
- **Helper scripts the user's agent may run:** Start skills marked for both audiences can also be run by Claude Code, outside every sandbox, possibly on text taken from an agent's result. `sympy-check` therefore checks every expression against an allowlist (numbers, names, operators, brackets, known SymPy functions) before SymPy parses it. Nothing else reaches the parser, and the allowlist is the only wall. The script also has a CPU limit of 10 s and rejects oversized powers and factorial-like calls before computing. That estimate works per power: a sum or product of many allowed powers and deeply nested expressions pass it and are stopped only by the CPU limit. Memory is not limited on macOS, which refuses the limit: an expansion can take a few GB for those 10 s.
- **Installing start skills:** "Add start skills", `arr init` and the project setup write only new files below `<workfolder>/skills/`, follow no link and leave nothing half written.
- **Updating start skills:** `arr skills update` replaces a start skill only if its folder equals, byte for byte, a version `arr` shipped (checksums of every shipped version are part of `arr`, none are stored in the workfolder). Any own file of the user, also a name starting with `.` or `_` except `.DS_Store` and `__pycache__`, makes the skill “changed”: it is never touched. It follows no link: a link, a file instead of a folder, or any link inside the skill counts as changed. The new version is built in a hidden folder next to it; right before the swap `arr` reads the old one again and leaves it if it changed. On a failure, also an interrupt between the two renames, the old version stays complete; if only removing the old version after the swap fails, the output names the hidden folder that is left. A change in the moment between that last check and the swap is lost with the old version.
- **Supervising agent (layer 4):** With the decider `gatekeeper_then_user` or `gatekeeper`, a model decides simple requests within the user's mandate. A fixed check runs first and does not trust the model. It lets through only network requests to the mandate's hosts (in v1 at most `pypi.org`, `files.pythonhosted.org`, `arxiv.org`) and single, plain `pip install` commands of PyPI names (checked against an allowlist following PEP 508/503, no files, paths, URLs or other indexes). Everything else goes to the user or is denied without a call.
  - The model can only allow once. It never decides run starts, escalations, questions to the user or Codex commands with extra rights.
  - The call runs the Claude CLI without tools, MCP servers, plugins or settings from agent-writable places. It gets a cleaned environment with no inherited login, address or session variables and the same outside hygiene as the other outside processes. The login comes only from the profile's start program.
  - Every call counts in usage per profile and against the budget, with at most 50 per run.
  - The kill switch knows the supervising agent's profile: blocking it stops the run and cancels a running call, whose answer then does not count.
  - Withdrawing a decision takes effect at once, also for requests already being checked.
  - The prompt shows only the asking agent's own history.
  - An agent or a phase can tighten the decider with `decider: user`, never loosen it. Its requests never reach the model. With `gatekeeper_then_user` they go to the user at once, with the verdict of the fixed check the user would see without the setting. With `gatekeeper` the fixed check still denies what it denies without the setting, and so does a decision the user withdrew; what lies within the mandate goes to the user, also when a limit of the model call applies (budget used up, 50 calls reached, blocked profile): the mandate stays the outer limit, and there is no call. When `arr` cannot tell which phase an agent is in, the user decides or the request is denied. An allow of the supervising agent never covers such a request, including the short allowance for package hosts after an installation it allowed, and an answer that arrives while the agent is tightened does not count. Such requests are no call and do not count against the 50 calls.
  - A run input can lift a skill's tightening (`defaults: {decider: null}`, its own `agents`, its own `phases`, or parameters that drop a phase). The run-start card lists every such lift as a sensitive deviation (see 5.2, no. 20).
  - The approval card in the terminal of `arr run` shows text that comes from an agent or from the supervising agent with control and format characters removed and line breaks made visible, so that such text cannot start a line of its own on the card. For a tightened request, the line that says why it is with the user is written by `arr`. The log keeps the raw text.
- **Agent text in the GUI:** The GUI holds the service token, so script in the page could click approvals for the user. All agent and skill text is rendered with every `<` escaped before Markdown. The HTML is then rebuilt from an allowlist of tags and attributes with no event handlers or styles; links may only be `http`, `https`, `mailto` or relative, and images only relative. Images from other addresses are shown as text and never loaded. A Content-Security-Policy on every response (`img-src 'self' data:`, `media-src 'self'`, `object-src 'none'`, `frame-src 'none'`, `script-src-attr 'none'`) is a second wall for images and event handlers. It does not stop `javascript:` links or inline scripts (NiceGUI writes inline scripts without a nonce), so for those the allowlist is the only wall.
  - Since W4b-07 the GUI shows runs with phases: the phase plan, submissions (summary, fields, file names, body excerpt), the summary of a phase escalation, questions in an agent's private channel and the fill level of a session. Every one of these values is escaped before it reaches the page; Markdown is rendered only through `markdown_html`, and no value is placed in an attribute unescaped. Agent text in these displays is cleaned by one rule (control and format characters, bidi controls and tag characters removed) before it is escaped. Texts from a `group.yaml` (task paths, format names, values of `choices`, route results), which a user or Claude Code may have written after reading agent text, are made one short line and escaped the same way. The view of submissions („Ergebnisse“) and `read_results` never show `note_next`; the transcript does (see "Agent text to Claude Code").
- **Codex project config:** `arr` records the state of the work folder's `.codex/` at run start and starts no further thread once it has changed.
- **Tests:** Escape tests run the real CLIs against a fake model server in a test `HOME` with random bait files, and check results by exit code only. A `security` stub keeps the real keychain out of every lab.

### 5.3 `KERN_PROCARGS2`

`KERN_PROCARGS2` is a kernel `sysctl` on macOS that returns the command line and the start environment of a process. `ps` uses it. For processes of the same user it needs no special rights. Apple's own system binaries do not expose their environment, but ordinary applications do.

This matters because some applications keep credentials in their environment, and a process inside the sandbox can read them.

Seatbelt cannot block this call. We tested seven rules, applied after process start: `deny sysctl-read` by name, prefix and regex, `deny process-info*` and `(deny default)`. The call succeeded under all of them, while counter-tests showed that the rules themselves were active. `arr` therefore keeps its own secrets out of every environment (principle 6), but it cannot protect secrets that other applications put there. The only fix we know of is layer 7.

**Measured in a spike (November 2026), not built yet.** A test account for agents, an ordinary account without admin rights, was probed with bait processes and bait files only:

- **The call is closed across accounts.** A process of the agent account cannot read the environment of a process of the user, and a process of the user cannot read that of the agent account. Counter-tests read their own bait in both accounts.
- **Inside the agent account it stays open.** Agents that all run under one account can read the environment of each other and of their own CLI. Principle 6 stays necessary.
- **The account does not protect files by itself.** Where the user's home folder is readable for other accounts, the agent account can read the files in it that have default permissions. The sandbox allowlist remains the first wall for files. The home folder has to be closed for the agent account before the account counts as a second one.
- **How agents are started matters.** Started with `sudo -u` from the user's login session, a process of the agent account runs inside that session: a keychain request opened a password dialog on the user's screen, which an agent could use for phishing. Started by a launchd daemon, the process runs outside the login session, and the same request failed at once without a dialog. That rules out `sudo` as the start path.
- **The agent account owns what it creates** and can lock `arr` out of those files. Reading, copying and deleting agents' files then needs a helper that runs under the agent account.
- **Processes:** one call under the agent account ended all of its processes, detached ones included, and none of the user's (way 4). It ends all runs at once.
- **Not measured:** the real agent CLIs and their sandbox under the agent account, and whether a process outside the login session can still show something on the user's screen through system-wide services.

**Until then:** this can include the application from which `arr` is started. Real runs therefore stay supervised until layer 7 exists.

## 6. Other platforms (template, not implemented)

The principles and layers carry over. These are the parts that change. Nothing here is implemented or measured yet.

| Concern | macOS (implemented) | Linux / server (to design) |
|---|---|---|
| OS sandbox | Seatbelt, Codex sandbox | Landlock, seccomp, bubblewrap or namespaces; containers or micro-VMs on servers |
| Credential store | Keychain | Secret Service (libsecret), files with strict permissions, a secret manager |
| Other processes' environment | `KERN_PROCARGS2`, not blockable by Seatbelt | `/proc/<pid>/environ`; hide with a PID namespace, `hidepid` or a separate user |
| Separate user | measured in a spike, not built | separate UID per run or per tenant, or one VM per run |
| Network | sandbox rules of the CLIs | network namespace, egress firewall with an allowlist |

On servers the Hugging Face lesson applies directly. A single allowed network path, such as a package proxy, is a target in its own right and needs the same adversarial testing as the sandbox.

## 7. Operating rules now

- Real runs are supervised. Hard problems run unsupervised only after layer 7.
- After stopping a run, check that none of its processes are left (way 4). A fresh work folder does not end the agent's background processes either.
- No shared work folder for Claude and Codex agents in one run.
- Do not write permission rules by hand that grant reading over an agent's own work folder: that makes it read-only for the Claude CLI.
- Agents cannot commit to git inside a run, because `.git` is write-protected for them. That is the price of the wall.
- Every change to sandbox, permissions or logins gets an escape test with a counter-test, and an independent review.
- Never test against real logins: test `HOME`, bait files, exit codes only. Every test that starts a real CLI runs in a lab with a `security` stub and no network except localhost (W4-04.1).
